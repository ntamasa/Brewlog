**Goal:** Load each brew's method in the same query as the page of brews, so listing a page costs one select (plus Spring Data's count query when the page is full), not one extra select per distinct method.

**Source (review of PR #4, round 3):**
- `Brew.method` is `@ManyToOne(fetch = FetchType.LAZY)` (`backend/src/main/java/com/brewlog/entity/Brew.java` line 35), and `BrewRepository` inherits `findAll(Pageable)` with no fetch join or entity graph. `BrewService.toResponse` (`backend/src/main/java/com/brewlog/service/BrewService.java` line 38) calls `brew.getMethod().getName()` and `getIconKey()`, so each distinct method on the page is loaded by its own select (up to 12 per page).
- Decided fix: `@EntityGraph(attributePaths = "method")` on `BrewRepository`'s `findAll(Pageable)` and `findAll(Specification<Brew>, Pageable)` overrides. The second is for BREW-43, whose `BrewService.list` calls `findAll(spec, pageable)` and so inherits the graph. `Brew.method` stays LAZY and the response stays the same.

## Hard logic
```java
// BrewRepositoryIT: run the query and read every method inside one transaction, so a lazy load would be counted
private Listed list(Function<BrewRepository, Page<Brew>> query) {
    Statistics stats = hibernateStatistics();
    return new TransactionTemplate(transactionManager).execute(status -> {
        stats.clear();
        Page<Brew> page = query.apply(brews);
        List<String> rows = page.getContent().stream()
                .map(b -> b.getName() + " | " + b.getMethod().getName() + " | " + b.getMethod().getIconKey())
                .toList();
        return new Listed(rows, page.getTotalElements(), stats.getPrepareStatementCount());
    });
}
```
Insert the brews before calling `list` (`jdbc` commits them on its own). Read the count inside the callback, after the rows are built.
