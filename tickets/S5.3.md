## Names and signatures
- Controls get `BREW_VALIDATORS`. `updateOn` stays `change`, but a control shows its error only when `submitted()` is true and the control is touched or dirty, so a field re-validates on blur or change after the first submit.
- The error state follows Form fields → Error state. `BrewForm` replaces BREW-101's `NO_ERROR_STATE` provider with `{ provide: ErrorStateMatcher, useExisting: forwardRef(() => BrewForm) }` and implements `isErrorState(control: AbstractControl | null): boolean`, which returns `this.submitted() && !!control && control.invalid && (control.touched || control.dirty)` and `fieldMessage(<the control's name, found in this.form.controls>)` isn't `null`, so a field never shows the red error state without a text.
- `submitted = signal(false)` and `banner = signal<FormBanner | null>(null)`, with `export type FormBanner = { kind: 'fields'; links: BannerLink[] }` and `export interface BannerLink { id: string; message: string }` in `brew-form.ts` (BREW-30 adds more kinds). The template renders the banner from `banner()` only. `banner` is set only by `submit()` and by the save's answer, never by a field change (B27): after a submit its count and links stay while the user fixes fields, until the next submit.
- `submit()`: `if (this.saving()) return;`, then `submitted.set(true)` and `form.markAllAsTouched()`. It never calls `updateValueAndValidity()` (that would drop the server errors BREW-112 sets). If `form.invalid`, it sends nothing and sets `banner` to `{ kind: 'fields', links }` (or `null` when `links` is empty), then focuses it. Otherwise it sets `banner` to `null` (the old banner hides while the request is in flight) and sends.
  - `links`: one `{ id, message }` per field whose `fieldMessage` isn't `null`, in form order.
  - Banner text: `n === 1 ? "1 field needs your attention" : n + " fields need your attention"`, with `n = links.length`, so singular only for exactly 1.
  - It holds one `<li><a href="#<id>">message</a></li>` per link.
  - The ids are those of Form fields: `name`, `bean`, `origin`, `method-btn`, `date`, `notes`; Rating's fieldset is `rating`, and the Roast level fieldset gets `id="roast"`.
  - The banner gets the focus (`tabindex="-1"`).
  - Clicking a link focuses that control: `#<id>` itself, or inside a fieldset its first `input[tabindex="0"]` or `button`.
- Each field's message is `fieldMessage(field: keyof BrewFormControls): string | null`, which returns `fieldErrorMessage(field, control.errors, field === 'name' ? control.value.trim() : undefined)` (BREW-26). The control names are the API field names (`name`, `beanName`, `origin`, `methodId`, `roast`, `rating`, `brewDate`, `notes`). The inline messages, `isErrorState` and the banner links all use it.
  - The `value` is the name as submitted, trimmed: a DUPLICATE on Brew name only lasts until Brew name changes (B27), so while it shows, `name.value.trim()` is the trimmed name of the request that got it. Typed "  kenyan morning " gives "You already have a brew called “kenyan morning”. Brew names must be unique, ignoring capitals." (R16's text).
  - Never pick the code with `Object.keys(errors)[0]`: the date control also carries Material's `matDatepickerMax` (from `[max]="today"`, which stays so the picker greys out later days) and `matDatepickerParse`, which `fieldErrorMessage` skips. So a typed future date shows "The date can’t be in the future" exactly once.
- A field whose message is `null` (no listed code, or a pair with no text, e.g. a server `{field:'methodId', code:'TOO_LONG'}`) renders no `mat-error` / `p.field-error`, is not in the error state (no `mat-form-field-invalid`, no `has-error` class), and isn't in the banner. The banner's `n` and links count only fields with a message, and the banner shows only when `n >= 1`.
- One message per field, one at a time:
  - Brew name, Bean name, Origin, Date and Tasting notes show it, inside `@if (message)`, as exactly one `<mat-error class="field-error"><mat-icon svgIcon="alert" aria-hidden="true" />{{ message }}</mat-error>` inside their `mat-form-field`. Material links it with `aria-describedby`, draws the red outline and the error-soft fill (`theme.scss`, BREW-100), and hides the hint meanwhile.
  - Brew method: `MethodSelect` gets `error = input<string | null>(null)`; `BrewForm` passes `[error]="fieldMessage('methodId')"`. Its `mat-select` gets `[errorStateMatcher]="errorMatcher"` with `errorMatcher: ErrorStateMatcher = { isErrorState: () => this.error() !== null }`, and its form field shows the same `mat-error` with `error()`. The constructor also adds `effect(() => { this.error(); this.matSelect().updateErrorState(); })`: `MatSelect.ngDoCheck` re-runs its matcher only when it has an ngControl (`select.mjs` lines 319–339), and this `mat-select` has none, so without the effect the field never gets `mat-form-field-invalid` or its `mat-error` (checked on Material 22.3.0). Don't give the inner `mat-select` a `formControl` instead: it would bypass `MethodSelect`'s CVA.
  - Roast level and Rating show `<p class="field-error">` with the same alert icon under their group, and their fieldset gets the class `has-error`.
  - `brew-form.scss` ports `components.css` line 110 as `.field.has-error .segmented { border-color: var(--color-error); background-color: var(--color-error-soft); }`.
  - `bean-rating.scss` ports line 127 as `:host-context(.field.has-error) .rating-input label { color: var(--color-error); }`.
- The save's `error` handler stays as it is (`saving.set(false)`, `form.enable()`). Setting the API's 400 field errors on the controls is BREW-112.
- Notes counter: shown when `notes.trim().length > 1800`, text `n.toLocaleString('en-US') + ' / 2,000'`, class `counter-error` when over 2000, `aria-live="polite"` region updated only when it appears and when it crosses 2000.
- Date input: an unparseable typed value leaves the control `null`, so it shows "Choose a date".

## Tests that prove it
**Seam:** component · **Setup:** TestBed + harnesses, `vi.setSystemTime(new Date(2026, 10, 1, 9, 0))`, the `MAT_FORM_FIELD_DEFAULT_OPTIONS` provider of BREW-100 · **Mocked:** HTTP (`HttpTestingController`)

Following Form fields → Tests:
- controls are found by id (`MatInputHarness.with({ selector: '#origin' })`)
- a field's message is `MatFormFieldHarness.with({ ancestor: '[data-field="origin"]' }).getTextErrors()`
- the error state is the form field's class `mat-form-field-invalid`
- the roast and rating messages are the `p.field-error` text in `[data-field="roast"]` and `[data-field="rating"]`

**Happy path**
1. Given an empty create form, when "Add to journal" is clicked, then no request is sent, the banner reads "6 fields need your attention" with links "Enter a brew name", "Enter a bean name", "Enter where the beans are from", "Choose a brew method", "Choose a roast level", "Choose a rating from 1 to 5 beans", the banner has focus, and each field shows its message (R13).
2. Given that state, when "Kenyan Morning" is typed in Brew name and the field blurs, then its error disappears and the banner count stays until the next submit (R13).
3. Given notes of 1801 characters, then the counter reads "1,801 / 2,000"; at 1800 there is no counter; at 2001 it reads "2,001 / 2,000" with `counter-error`, and the text is not cut off (R15).

**Negative**
