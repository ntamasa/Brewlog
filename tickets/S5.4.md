## Names and signatures
- There is no `serverErrors` signal. The controls' errors are the one source. In the save's `error` handler, in this order:
  1. `saving.set(false)`.
  2. `form.enable()`. It re-runs every validator, so it must come before the server errors are set, or it would drop them.
  3. If `parseApiError(err).kind === 'fields'`: group its `{field, code}` pairs by field. Keep only pairs whose `field` is a key of `form.controls` and whose `brewFieldMessage(field, code, field === 'name' ? name.value.trim() : undefined)` isn't `null`. Drop the others: they have no text to show and must not block sending. Call `control.setErrors({ [code]: true, ... })` once per field, with all its kept codes.
  4. Set `banner` to `{ kind: 'fields', links }` built as in `submit()` (`null` when empty), then focus it.
  - Other answers (`notFound`, `protected`, `network`): only steps 1 and 2. `banner` stays `null` (BREW-30 adds the server banner).
  - Clearing needs no code of its own. Any value change of a control re-runs its validators, which replace its errors and remove the server code. Until then the control stays invalid. So `form.invalid` is true, and the next `submit()` sends nothing and lists the field in the client banner like a client error.
  - Nothing may re-run the validators of an unchanged control: no `updateValueAndValidity()`, no `setValue` / `patchValue` with the same value, and no `enable()` or `reset()` outside step 2.

## Tests that prove it
**Seam:** component · **Setup:** as BREW-27's tests (TestBed + harnesses, `vi.setSystemTime(new Date(2026, 10, 1, 9, 0))`, the `MAT_FORM_FIELD_DEFAULT_OPTIONS` provider of BREW-100, controls and messages found as Form fields → Tests says); "no request" is `httpTesting.expectNone('/api/brews')` · **Mocked:** HTTP (`HttpTestingController`)

**Happy path**
1. Given a filled form whose POST answers 400 `{errors:[{field:'origin',code:'TOO_LONG'}]}`, then Origin shows "Origin can be at most 100 characters" and the form keeps every value (R15, R50).
2. Given a filled form with Brew name "  kenyan morning " whose POST answers 400 `{errors:[{field:'name',code:'DUPLICATE'}]}`, then Brew name's `getTextErrors()` is exactly `["You already have a brew called “kenyan morning”. Brew names must be unique, ignoring capitals."]`, its form field has `mat-form-field-invalid`, and every field keeps its value (R16 text, R50).
3. Given test 2's state, when Brew name is changed to "Kenyan Evening", then Brew name has no `mat-error` and no `mat-form-field-invalid`, and the banner is unchanged. When "Add to journal" is clicked, then the banner is gone while exactly one POST `/api/brews` with `name` "Kenyan Evening" is pending (R50, B27).
4. Given test 1's state, when Origin is changed to "Kenya", then Origin has no `mat-error` and no `mat-form-field-invalid`, and the banner still reads "1 field needs your attention". When "Add to journal" is clicked, then a POST with `origin` "Kenya" is sent (R50).

**Negative**
5. Given a filled form whose POST answers 400 `{errors:[{field:'origin',code:'TOO_LONG'},{field:'methodId',code:'TOO_LONG'}]}`, then Origin shows "Origin can be at most 100 characters", the method form field has no `mat-error` and no `mat-form-field-invalid`, and the banner reads "1 field needs your attention" with exactly one link "Origin can be at most 100 characters" (R15).
6. Given test 2's state, when "Add to journal" is clicked again without any change, then no request is sent, the banner reads "1 field needs your attention" with exactly one link "You already have a brew called “kenyan morning”. Brew names must be unique, ignoring capitals.", and focus is on the banner (R50).
7. Given test 1's state, when only Bean name is changed (to "AA Kiambu"), then Origin still shows "Origin can be at most 100 characters" with `mat-form-field-invalid`. When "Add to journal" is clicked, then no request is sent, the banner reads "1 field needs your attention" with exactly one link "Origin can be at most 100 characters", and focus is on the banner (R50).
8. Given test 1's state, when Brew name is cleared and "Add to journal" is clicked, then no request is sent and the banner reads "2 fields need your attention" with the links "Enter a brew name" and "Origin can be at most 100 characters", in that order (R50, R13).
9. Given test 5's state, when Origin is changed to "Kenya" and "Add to journal" is clicked, then a POST is sent: the dropped `methodId` `TOO_LONG` pair doesn't block it (R50).
10. Given a filled form whose POST fails with status 0, then no field has a `mat-error` or `mat-form-field-invalid`, no banner shows, the fields are enabled and keep their values (R50: only `fields` answers set errors).
