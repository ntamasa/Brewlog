**Goal:** Publish the compose `db` port on the host's loopback only, so the LAN can't reach Postgres with its known password.

**Source (review of PR #3):** Technical design → Deployment below, `docker-compose.yml` bullet: "port `127.0.0.1:5432:5432` (host loopback only, so the LAN can't reach Postgres with its known password while a backend run outside Compose still finds it on `localhost:5432`; from grilling)". It replaces BREW-9's Done-when check "`docker compose config` shows `db` with the port `5432:5432` (published 5432, target 5432)", which check 1 below takes over.

**Read first:**
- Technical design → Deployment, below
- Story → Constraints (single user, local or private deployment), Epic → Technical design → Risks

## Files that change
- modify `docker-compose.yml`: under `db`, `ports:` holds the single entry `- "127.0.0.1:5432:5432"` (was `"5432:5432"`). Nothing else in the file changes.

## Tests that prove it
**Seam:** compose config and the running stack, from the repo root · **Setup:** Docker Desktop running (Story → Prerequisites) · **Mocked:** nothing

**Happy path**
1. When `docker compose config` runs, then `db.ports` has exactly one entry with `host_ip: 127.0.0.1`, `target: 5432`, `published: "5432"`, `protocol: tcp`; `db` still mounts `brewlog-data` at `/var/lib/postgresql/data`, and `brewlog-data` is still under the top-level `volumes:`.
2. Given `docker compose down -v && docker compose up -d --build --wait`, when `docker compose port db 5432` runs, then it prints `127.0.0.1:5432`; and `cd e2e && npx playwright test` passes in both projects (the backend still reaches Postgres on `db:5432` inside the compose network).

**Negative**
3. Given the stack from test 2, `docker compose ps db` shows `127.0.0.1:5432->5432/tcp` and no `0.0.0.0:5432` or `[::]:5432` binding.
4. `docker compose config` still shows no `ports` on `backend` and `8081:80` on `frontend` (unchanged).

## Out of scope
- `backend/src/main/resources/application.yml`: its default `jdbc:postgresql://localhost:5432/brewlog` stays and still works against the published loopback port.
- The workflows (previous subtask).

## Done when
- Checks 1–4 hold, then `docker compose down -v` cleans up.
