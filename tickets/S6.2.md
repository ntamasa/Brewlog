## Names and signatures
- BREW-27's `export interface FormBanner { kind: 'fields'; links: BannerLink[] }` becomes the union `export type FormBanner = { kind: 'fields'; links: BannerLink[] } | { kind: 'duplicate' } | { kind: 'methodGone' } | { kind: 'server' }` (a union may be a `type`; the interface goes). `banner` stays set only by `submit()` and by the save's answer (B27, R50): a field change never hides or changes any banner. `submit()` replaces it with the client banner when the form is invalid (server errors still on their unchanged fields count, BREW-112), or with `null` when it sends.
- The answer handler keeps BREW-112's order: `saving.set(false)`, `form.enable()`, then the field errors, then `banner` and its focus. For a `fields` answer, BREW-112's step 3 sets every kept field error, and the banner of step 4 is, first match wins:
  - `name` `DUPLICATE` among the pairs → `{ kind: 'duplicate' }`: "Couldn’t save your changes" + the link "That brew name is already taken" (to `#name`). The name error `{ DUPLICATE: true }` shows in Brew name's `mat-error` through BREW-27's `fieldMessage('name')`, with the trimmed name: "You already have a brew called “kenyan morning”. Brew names must be unique, ignoring capitals."
  - `methodId` `METHOD_NOT_FOUND` among the pairs → `{ kind: 'methodGone' }`: before step 3, `MethodStore.load()` and `methodId.setValue(null)`. The `setValue` re-runs the validators, so it must come before step 3 sets `{ METHOD_NOT_FOUND: true }`. `MethodSelect`'s `error` then shows "This method no longer exists. Choose another one." with the error outline. The banner reads "Couldn’t save your brew" + the link "This method no longer exists" (`href="#method-btn"`) + ". Choose another one." Choosing a method changes `methodId`, which drops that error (B27).
  - otherwise BREW-112's `fields` banner.
- `network` (status 0, 5xx, 400 without errors) → `{ kind: 'server' }`: "Couldn’t save your brew" + "The Brewlog server didn’t respond. Nothing was lost: your entry is still here, so you can try again."; no toast; `saved` is not emitted.
- Every banner gets focus; the fields keep their values; `saving` is reset.

## Tests that prove it
**Seam:** component (`BrewForm`) · **Setup:** TestBed + harnesses, real `BrewApi`, `MethodStore` · **Mocked:** HTTP (`HttpTestingController`), `Toaster` (`{ provide: Toaster, useValue: { show: vi.fn() } }`, BREW-104) · controls and messages found as Form fields → Tests says (`#name`, `[data-field="method"]`), with the `MAT_FORM_FIELD_DEFAULT_OPTIONS` provider of BREW-100

**Happy path**
1. Given a filled form named "kenyan morning", when the POST answers 400 `{errors:[{field:'name',code:'DUPLICATE'}]}`, then the banner reads "Couldn’t save your changes" with "That brew name is already taken", the name error reads "You already have a brew called “kenyan morning”. Brew names must be unique, ignoring capitals.", every field keeps its value and `saved` is not emitted (R16).
2. Given method Moka Pot selected, when the POST answers 400 `methodId` `METHOD_NOT_FOUND`, then GET `/api/methods` is sent, the select shows "Choose a method", its form field has `mat-form-field-invalid` and its `mat-error` reads "This method no longer exists. Choose another one.", the banner reads "Couldn’t save your brew", and the other fields keep their values (R19).
3. Given that state, when AeroPress is chosen and "Add to journal" clicked, then the method error is gone and a POST with `methodId` 4 is sent (R19).

**Negative**
4. Given the POST fails with status 0, then the banner reads "Couldn’t save your brew" / "The Brewlog server didn’t respond. Nothing was lost: your entry is still here, so you can try again.", the fields keep their values, the button reads "Add to journal" again and `Toaster.show` isn't called (R20).
5. Given the POST answers 500, then the same server banner shows (R20).
6. Given the POST unflushed, then the button reads "Saving…" with `aria-busy="true"` and all inputs are disabled (R20).
